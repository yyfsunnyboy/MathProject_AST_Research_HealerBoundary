# AI 生成程式共同失敗分類標準（實際使用版 v3）

> 適用範圍：CE115（Math16）、MBPP+、HumanEval+ 與後續同類 Python 程式生成資料集  
> 版本日期：2026-07-20  
> 文件性質：跨專案共同 codebook；不取代各專案的正式 manifest、evaluator、凍結規格與原始結果  
> 核心目的：以共同欄位記錄失敗症狀、錯誤機制、責任歸因與 Healer 結果，同時維持既有研究結果的不可變性

---

## 0. 使用聲明與不可竄改原則

本版是分類標準的修訂，不是對既有 CE115、MBPP+ 或 HumanEval+ 結果的重新評分。使用 v3 時必須遵守：

1. 原始 response、candidate、first-attempt 結果、舊分類、舊統計、manifest 與 hash 均不可覆寫。
2. v3 新欄位只能新增為衍生 annotation、crosswalk view 或新的 evaluation revision。
3. 若需依 v3 重新檢視舊案例，必須保留 `legacy_failure_category`，另寫 `v3_classification_revision`、判定者、日期與證據；不得把新標籤偽裝成當時已存在的結果。
4. evaluator 修正可用原始 first-attempt artifact 離線重評，但須建立新 revision；prompt 或任務契約改變則須建立新 run，不得併入舊 run。
5. 不同資料集、模型、prompt condition、資料角色與 evaluator revision 不得混算分母。
6. 本文件的 L0–L5 是「失敗症狀／最早阻斷層」；不是 Healer 實作中的規則層級編號。若專案另有同名 Healer layer，報告時必須加前綴區分，例如 `failure_layer=L2`、`healer_rule_layer=H3`。

---

## 1. 四個必須分開記錄的維度

每個 cell 至少分開記錄下列四件事，不得用單一分類名稱同時代替：

| 維度 | 回答的問題 | 主要欄位 |
|---|---|---|
| 症狀層級 | 最早在哪個 gate 被阻斷？ | `primary_failure_layer`、G1–G4 |
| 錯誤機制 | 為什麼會出現該症狀？可否跨層？ | `mechanism_tags`、`failure_subtype` |
| 責任歸因 | 結果可否歸因於模型？ | `outcome_validity`、`responsibility_notes` |
| Healer 處理 | 是否符合修復資格、是否修改、結果如何？ | `healer_eligibility`、`healer_decision`、`healer_outcome` |

例如，「截斷」是機制，不是固定層級；「Entry-point 錯誤」是 L2 Contract 症狀，但是否可修仍要另看候選是否唯一；「修後 PASS」是 Healer 結果，不會改變原始 first-attempt 的 L2。

## 2. 正式通過標準 G1–G4

| Gate | 名稱 | 判定內容 |
|---|---|---|
| G1 | Parse / Candidate | 是否取得可判定的 Python candidate，且能建立 AST |
| G2 | Execution | 在凍結環境與資源限制內，程式能否完成要求的執行而不發生例外或逾時 |
| G3 | Contract | Entry point、函式名稱與簽名、required API、回傳型別、schema、packaging 與 canonical form 是否符合事前契約 |
| G4 | Correctness | 是否通過凍結的 oracle、單元測試或 benchmark tests |

只有所有適用 gate 均 PASS，才可標 `final_status = PASSED`。不適用的子 gate 填 `NOT_APPLICABLE`，不可留空。

### 2.1 Gate 是判定條件，不是只能線性執行的程式順序

G3 同時包含可在執行前檢查的介面契約，以及執行後才能檢查的輸出契約：

- `G3e entry-point/signature`：解析後即可檢查，應先於呼叫 candidate。
- `G3a required-API adoption`：只有任務事前明文規定 required API 時才適用。
- `G3s output schema/packaging`：通常在執行成功後檢查。
- `G3c canonical form`：只有契約明文要求時適用，且須用語意等價的正規化方法判定。

因此 evaluator 因找不到指定函式而產生的 `NameError` 或 `AttributeError`，不能只看例外名稱就標 L4；若根因是 entry point 不符，應標 G3e FAIL／L2。

### 2.2 Canonical form 原則

- 標準呈現形式屬 G3／L2，不屬 L5。
- 不可只用原始字串全等否決語意等價答案；須先做契約允許的正規化。
- 若結構或數值本身錯誤，仍屬 G4／L5，不得以格式正規化放行。
- HumanEval+、MBPP+ 若無額外 canonical-form 契約，填 `NOT_APPLICABLE`。

## 3. outcome_validity：結果有效性與責任歸因

`outcome_validity` 是責任歸因，不是錯誤層級。

| 值 | 定義 | 是否計入模型表現統計 |
|---|---|---|
| `VALID_MODEL_OUTCOME` | 在有效契約、evaluator 與基礎設施下，結果可歸因於模型輸出 | 是 |
| `INVALID_EVALUATOR` | oracle、測試、正規化或判分邏輯錯誤，造成誤判或誤放 | 否；須修正並建立 revision |
| `INVALID_CONTRACT` | prompt、API 文件、函式介面、schema 或任務契約錯誤／矛盾／不足，直接造成結果不可公平歸因 | 否；須修契約並另行驗證 |
| `INVALID_INFRASTRUCTURE` | 模型服務、runner、extractor、序列化、檔案或執行環境故障 | 否 |
| `PENDING_REVIEW` | 現有證據不足，尚不能歸因 | 暫不計入；正式合併分析前應裁決或明列未裁決數 |

### 3.1 症狀層與 validity 可正交組合

- 模型輸出含多餘自然語言、導致無法解析：L1 + `VALID_MODEL_OUTCOME`。
- extractor 誤切合法程式、導致無法解析：L1 + `INVALID_INFRASTRUCTURE`。
- 模型遵循錯誤 API 文件後崩潰：依症狀標 L3，validity 為 `INVALID_CONTRACT`。
- 正確答案被 evaluator 的字串全等誤殺：觀察上可能停在 G4，但 validity 為 `INVALID_EVALUATOR`；不得列入模型 L5 失敗率。

### 3.2 Revision 規則

1. 原始 artifact 與原始判定永不改寫。
2. evaluator 修正後，以原 first-attempt artifact 離線重評，寫入新的 `evaluation_revision_NNN`。
3. revision 必須保存舊／新 evaluator hash、受影響 cells、修正理由、測試與前後對照。
4. prompt 或契約內容改變時，不能僅離線重評；須建立新的 `run_id`，並標明 evidence role。
5. revision 只修正評測錯誤，不得為提高通過率而放寬真實 correctness 標準。

## 4. 共同失敗層級 L0–L5

### L0：Infrastructure Failure

模型生成或評測流程未可靠完成，尚不能判定 candidate 的程式能力。

常見情況：模型 API／Ollama 呼叫失敗、服務 timeout、runner 中斷、raw response 不存在、檔案寫入失敗、系統資源錯誤。

```text
infrastructure_valid = false
G1–G4 = NOT_ASSESSED（除非已有可獨立驗證的前段證據）
outcome_validity = INVALID_INFRASTRUCTURE
```

規則：

- 保留在 ITT 分母；可依預先規定從 valid-response 分母排除。
- 不送入 Healer。
- 合法的基礎設施重試須事前固定上限與政策，保存所有 attempt metadata；重試耗盡才標 L0。
- 模型產生了完整 raw response，但研究方 extractor 錯誤，不應因責任在系統就一律改標 L0；仍依可觀察症狀標 L1／L2，另以 `INVALID_INFRASTRUCTURE` 歸責。

### L1：Candidate / Parse / Syntax Failure

已有模型輸出，但無法取得可判定的 Python candidate，或 candidate 無法建立 AST。

常見情況：`SyntaxError`、`IndentationError`、括號／字串未關閉、非法語法、無法排除的 Markdown／自然語言污染、多段程式且無法選定、截斷後無法解析。

```text
G1 = FAIL
G2–G4 = NOT_ASSESSED
```

注意：

- Format／packaging 只有在阻止可靠 candidate extraction 或 parsing 時才是 L1。
- `truncation` 在此只是 mechanism tag；不是所有截斷都自動屬 L1。
- 一般語法錯誤也不因「看起來容易補」就自動成為 Healer eligible。

### L2：Contract / Entry-point / Output Packaging Failure

Python candidate 可解析，但違反事前明確的程式介面或輸出契約。L2 可在正式執行前由 G3e 發現，也可在執行成功後由 G3s／G3c 發現。

常見情況：

- 指定 entry point 缺失、名稱錯誤或 signature 不符；
- 應回傳 dict 卻回傳 scalar／string；
- 缺必要 key、多包或少包一層；
- `correct_answer` 或其他欄位型別錯誤；
- nested schema 錯誤；
- dict 被 `json.dumps()` 包成字串；
- 經允許的語意等價正規化後，canonical form 仍不符。

典型 gate：

```text
G1 = PASS
G3e = FAIL                         # entry point / signature
或
G1 = PASS, G2 = PASS, G3s/G3c = FAIL  # output schema / packaging
G4 = NOT_ASSESSED
```

#### Entry-point 的固定歸類與 eligibility

Entry-point 錯誤明確歸 L2 Contract，不因 harness 最後拋出 `NameError`／`AttributeError` 而改歸 L4。

只有同時滿足下列條件，才可標 `healer_eligibility = eligible`：

1. 任務契約明文指定唯一 required entry point 與 signature；
2. required entry point 缺失或名稱不符；
3. candidate 中恰有一個結構上相容的安全候選；
4. 修法只是唯一的 alias／rename／薄 wrapper，保留原函式主體、參數資料流與回傳值；
5. eligibility 判定未使用 oracle、測試成敗、hidden tests 或 reference answer；
6. 規則已具有正例、反例、ambiguous／do-not-repair 測試並在正式測試前凍結。

若存在零個或多個合理候選、重複定義／shadowing 使綁定不清楚、signature 無法唯一對應，則：

```text
primary_failure_layer = L2
mechanism_tags += ["entry_point_mismatch", "ambiguous_entry_point"]
healer_eligibility = noneligible
healer_decision = abstained
```

「安全候選 42」與「模糊候選 4」必須分開，不能因同屬 Entry-point 就一律修復。

### L3：Domain API / Tool-use Failure

程式對任務提供或要求的 Domain API／工具契約使用錯誤。L3 是以錯誤來源判定的領域工具層，可在 G2、G3a 或 G4 顯現。

包含：

- Domain API／tool import 路徑或名稱錯誤；
- API 名稱、arity、型別、input grammar 或 argument shape 錯誤；
- required API 未使用；
- 選錯工具、本地重寫或遮蔽 required API；
- partial adoption；
- 臆測不存在的 API 回傳形狀；
- API 結果未接入必要資料流。

判定型態：

```text
型一：G1 PASS, G2 FAIL
      例外可直接追溯至 Domain API／tool 的 import 或呼叫契約。

型二：G1 PASS, G2 PASS, G3a FAIL
      任務事前明定 required API，但模型未採用或以本地版本取代。

型三：G1 PASS, G2 PASS, G3 PASS, G4 FAIL
      錯誤值可追溯至 API 選擇、參數或結果流，但非一般演算法錯誤。
```

Import 規則：

- Domain API／tool 的 import 或使用錯誤 → L3。
- 一般 Python 標準庫、允許依賴或模型自有 helper 遺漏 import，執行時造成 `NameError` → 通常 L4。
- import statement 本身無法解析 → L1。
- 契約禁止外部依賴而模型仍使用 → 依明文契約通常為 L2，並加 `unauthorized_dependency`；若實際最早只在執行時發現，須記錄 failure chain。
- 執行環境遺漏契約明允許且應提供的套件 → 依症狀層標記，`outcome_validity = INVALID_INFRASTRUCTURE`。

Validity 規則：

- prompt 的 API 文件與 runtime 不一致 → `INVALID_CONTRACT` + `prompt_api_mismatch`。
- 文件正確、模型仍臆測或誤用 → `VALID_MODEL_OUTCOME`。
- 裁決前必須核對模型實際看到的 API 文件與凍結 runtime 簽名。

### L4：Runtime / Assembly / Data-flow Failure

candidate 可解析，且不存在更早的 entry-point／contract 阻斷，但模型程式在執行時因一般程式組裝、資料流或控制流程錯誤失敗。

常見情況：一般 `NameError`、`KeyError`、`TypeError`、`IndexError`、`RecursionError`、無限迴圈、candidate execution timeout、未定義變數、錯誤資料結構取值、參數來源錯誤、錯誤遞迴、一般 missing import、code bloat 引發 runtime 問題。

```text
G1 = PASS
G2 = FAIL
G3/G4 尚未能完整判定
```

與相鄰層的界線：

- 指定 entry point 缺失 → L2，不是 L4。
- Domain API／tool 契約的 import 或呼叫錯誤 → L3。
- 一般遺漏 import 造成 `NameError` → 通常 L4。
- 系統序列化或 evaluator bridge 接不住合理輸出 → 症狀層照標，validity 為 `INVALID_INFRASTRUCTURE` 或 `INVALID_CONTRACT`。

### L5：Semantic / Answer Incorrect Failure

程式可解析、可執行、介面與輸出契約正確，但答案或演算法未通過正式 correctness evaluator。

常見情況：數學公式錯誤、一般演算法錯誤、邊界條件漏處理、硬編碼錯誤答案、錯誤模式匹配、HumanEval+／MBPP+ tests 未通過、目標偏移、參數語義錯置。

```text
G1 = PASS
G2 = PASS
G3 = PASS
G4 = FAIL
outcome_validity = VALID_MODEL_OUTCOME（確認 evaluator 有效後）
```

規則：

- `Unknown` 不得直接映射成 L5；只有完成 G1–G4 逐層判斷並確認前三 gate 通過後，才能標 L5。
- G4 FAIL 前須排除 L2 schema／packaging 問題與 `INVALID_EVALUATOR`。
- L5 原則上在 deterministic Healer 邊界外；需要重解題、依測試反推或重建模型意圖的修改一律 abstain。

## 5. Truncation：跨層 mechanism tag

`truncation` 表示輸出內容疑似或確定因 token／stop／傳輸等原因提前終止。它描述「怎麼形成」，不描述「最早在哪一層失敗」。

| 截斷後的可觀察結果 | primary layer | 例示 |
|---|---|---|
| 無法取得可解析 candidate | L1 | 括號、字串、函式主體未閉合 |
| 可解析，但 required entry point／signature 因截斷缺失 | L2 | 指定函式未完整產生 |
| 可解析，但 Domain API／tool 呼叫片段不完整 | L3 | 依具體 API 證據判定 |
| 可解析，但執行時因缺少定義、return path 或組裝片段而失敗 | L4 | `NameError`、缺失資料流、非終止 |
| 可執行且 contract 正確，但邏輯／case coverage 不完整而答錯 | L5 | 演算法只完成部分分支 |

標記規則：

- 有明確證據才用 `truncation`；證據不足用 `possible_truncation`，並標 `PENDING_REVIEW` 或補充 notes。
- `truncation` 可與任何 L1–L5 共存，不參與 L0–L5 互斥計數。
- Stage2 的 Truncation 80 是既有重疊標記，不是第七個互斥 failure category，也不得加入其他類別求和。

### 5.1 Healer 邊界

- 刪除「截斷補全是安全 Healer」的預設說法。
- 截斷代表內容可能已遺失；補齊通常需要猜測模型意圖或重新生成，因此原則上 `healer_eligibility = noneligible`、`healer_decision = abstained`。
- 不能因只差一個括號、return 或幾行程式就自動宣稱語意不變。
- 未來若另行提出極窄、可證明唯一且不補入新語意的規則，必須以新 rule ID、獨立 safety proof、do-not-repair tests、validation 與凍結版本審查；不得回頭把既有 80 筆改算為 eligible 或 rescue。

## 6. Format／Packaging 的最早 gate 拆分

`Format／packaging` 是舊分類，v3 不再把它直接等同單一 layer。

| 實際症狀 | v3 layer | mechanism_tags 範例 |
|---|---|---|
| Markdown fence、說明文字、多段候選或抽取邊界使 candidate 無法可靠解析 | L1 | `format_contamination`, `candidate_extraction_failure` |
| candidate 可解析，但指定 callable、signature、return schema、容器或 canonical form 不符 | L2 | `entry_point_mismatch`, `output_packaging`, `schema_mismatch` |
| 研究方 extractor／包裝器破壞原本合法程式 | 依症狀為 L1 或 L2 | 加 `pipeline_extraction_error`，validity=`INVALID_INFRASTRUCTURE` |

不可僅憑舊字串標籤把既有 68 筆全部改成 L1 或 L2；必須逐筆依最早 gate 判定，並以新 revision 保存。未重審前只保留 `legacy_failure_category = Format/packaging`。

## 7. Unknown 的處理

`Unknown` 只代表舊資料尚未完成根因裁決，不代表語意錯誤。

判定順序：

1. 基礎設施是否有效？否 → L0。
2. candidate 能否可靠抽取與解析？否 → L1。
3. entry point／signature 等可前置檢查的 contract 是否符合？否 → L2。
4. 執行是否成功？若否，Domain API／tool 證據充分 → L3；一般 runtime／assembly → L4。
5. 執行後 schema、packaging、canonical form 是否符合？否 → L2。
6. required API 是否符合？否 → L3。
7. G1–G3 均 PASS，正式 correctness 仍 FAIL，且 evaluator 有效 → L5。

若證據不足：

```text
legacy_failure_category = Unknown
classification_status = PENDING_REVIEW
primary_failure_layer = null
outcome_validity = PENDING_REVIEW
mechanism_tags += ["needs_human_review"]
```

`primary_failure_layer = null` 只允許作過渡／歷史缺證狀態；不得納入 L0–L5 分布。若原始 artifact 已不可取得，應永久保留 legacy Unknown 並在報告中列為未能 crosswalk，而不是補猜 L5。

## 8. Mechanism tags 共同字典

Mechanism tags 可多選、可跨層，不能取代 `primary_failure_layer`。

| 類群 | 建議標籤 | 意義 |
|---|---|---|
| 產出完整性 | `truncation`, `possible_truncation`, `code_bloat` | 提前終止、疑似提前終止、異常膨脹 |
| 擷取／格式 | `format_contamination`, `candidate_extraction_failure`, `pipeline_extraction_error` | 程式外文字、多候選、研究方抽取問題 |
| Contract | `entry_point_mismatch`, `ambiguous_entry_point`, `signature_mismatch`, `output_packaging`, `schema_mismatch`, `canonical_form_mismatch`, `unauthorized_dependency` | 介面與輸出契約問題 |
| Domain API | `invalid_api_call`, `domain_api_import_error`, `tool_routing_failure`, `local_api_shadowing`, `partial_adoption`, `return_shape_hallucination`, `api_result_disconnected`, `prompt_api_mismatch` | 工具採用與組裝問題 |
| Runtime | `general_missing_import`, `undefined_name`, `wrong_parameter_source`, `control_flow_failure`, `recursion_failure`, `execution_timeout`, `model_assembly_failure` | 一般程式執行／資料流錯誤 |
| Semantic | `algorithmic_error`, `edge_case_omission`, `mathematical_error`, `hardcoded_wrong_answer`, `semantic_goal_drift`, `parameter_semantics_swap` | G4 correctness 錯誤 |
| 治理 | `answer_leak`, `needs_human_review` | 答案洩漏或證據不足 |

使用原則：

- `missing_import` 舊標籤應在 v3 拆成 `domain_api_import_error` 或 `general_missing_import`。
- 例外型別不是根因；不能看到 `NameError` 就跳過 entry-point／Domain API 判斷。
- 同一 cell 可有多個 mechanism tags，但只有一個 raw first-attempt `primary_failure_layer`。

## 9. Failure chain：多層錯誤與階段轉移

`failure_chain` 保留同一 cell 在不同處理階段可觀察到的失敗，不覆蓋 raw 主分類。

建議 v3 使用結構化記錄：

```json
{
  "primary_failure_layer": "L4",
  "failure_chain": [
    {
      "stage": "raw_first_attempt",
      "layer": "L4",
      "gate": "G2",
      "mechanism": "wrong_parameter_source",
      "outcome_validity": "VALID_MODEL_OUTCOME"
    },
    {
      "stage": "post_healer_rule_1",
      "layer": "L2",
      "gate": "G3s",
      "mechanism": "output_packaging",
      "outcome_validity": "VALID_MODEL_OUTCOME"
    },
    {
      "stage": "post_healer_rule_2",
      "layer": null,
      "gate": "G1-G4",
      "mechanism": null,
      "final_status": "PASSED"
    }
  ]
}
```

規則：

- raw `primary_failure_layer` 永遠維持最早可觀察失敗層。
- 修掉前層後暴露的後層問題，只加入 chain，不回寫 raw layer。
- `changed_partial_progress` 代表 gate 前進，不等於 rescue。
- pipeline correction、evaluator revision、Healer transformation 必須標明不同 stage。
- 舊版字串陣列可保留；v3 匯出時可另產生 structured chain，不必修改舊欄位。

## 10. Healer eligibility、決策與結果

### 10.1 三個欄位不得混用

| 欄位 | 建議值 | 意義 |
|---|---|---|
| `healer_eligibility` | `eligible`, `noneligible`, `undetermined` | 在不知道 evaluator 結果時，是否符合凍結安全規則 |
| `healer_decision` | `transformed`, `abstained`, `no_trigger`, `rejected`, `not_run` | Healer 實際採取什麼動作 |
| `healer_outcome` | `rescue_to_pass`, `changed_partial_progress`, `preserved_pass`, `unchanged_fail`, `regression`, `rollback`, `not_assessed` | 同一 evaluator 下修前／修後的配對結果 |

v2 的 `noneligible`、`no_trigger`、`abstained` 實際混合了資格、動作與結果；既有值可保留於 `legacy_healer_outcome`，v3 衍生欄位另行拆分。

### 10.2 Eligibility 必要條件

候選規則至少同時滿足：

1. Local：修改局部且可明確定位。
2. Deterministic：相同輸入得到相同轉換。
3. Answer-free：不使用 oracle、官方答案、失敗測資或 reference solution 反推。
4. Task-agnostic：不依 task ID、seed 或單題常數硬編碼。
5. Unique／Conservative：修法唯一，不猜測模型意圖。
6. Invariant-supported：有可說明的語意或介面不變量。
7. Tested：有正例、反例、ambiguous 與 do-not-repair 測試。
8. Frozen：正式測試前固定規則、順序、版本與 hash。
9. Evaluator-blind：eligibility 與 transformation 看不到該 cell 的正式 pass/fail、hidden tests 或答案。
10. Re-evaluated：修後重新跑同一版本的所有適用 G1–G4。

任一條不滿足時，預設 abstain。

### 10.3 各 failure layer 的原則

| Layer | 原則 |
|---|---|
| L0 | 不送 Healer |
| L1 | 只有可證明唯一且語意不變的既有凍結規則才可能 eligible；truncation 原則上 abstain |
| L2 | 主要候選區，但 entry point／schema 仍須通過唯一性與契約明確性檢查 |
| L3 | 僅 `VALID_MODEL_OUTCOME` 且局部唯一者可能 eligible；`INVALID_CONTRACT` 應先修契約，不算 rescue |
| L4 | 僅機械、唯一的接線錯誤可能 eligible；需重建控制流程者 abstain |
| L5 | 原則上不修；需重新解題或改寫演算法者一律 abstain |

### 10.4 Healer 觸發率的正確解釋

「Healer 高觸發率必然代表系統不成熟」不成立。應依 `outcome_validity` 分層解釋：

- `INVALID_CONTRACT`／`INVALID_EVALUATOR`／`INVALID_INFRASTRUCTURE` 相關觸發偏高，才支持評測系統、契約或管線仍有問題；這些修正不得算成模型 Healer rescue。
- `VALID_MODEL_OUTCOME` 的高觸發率，可能表示模型穩定違反一個已明確、有效且可安全修復的契約；這是模型行為與 Healer 介入窗口的證據，不可直接說成評測系統不成熟。
- 觸發率本身不代表有效性；必須同時報 eligible、transformed、rescue、partial progress、regression、false positive 與 abstention。

## 11. 舊分類到 v3 L0–L5 的 crosswalk

Crosswalk 是相容與待重審規則，不是回頭改寫既有統計。

| legacy_failure_category | 既有 Stage2 數量 | v3 crosswalk | mechanism_tags／Healer 原則 |
|---|---:|---|---|
| `Format/packaging` | 68 | 不能整批映射；阻止抽取／parse → L1；可解析但 entry point／schema／packaging 違約 → L2 | 保留原 68；逐筆重審才產生 v3 衍生分布 |
| `Syntax` | 60 | 通常為 L1，但須以 G1 FAIL 證據確認；若實為可解析後的 `NameError`，不得硬留 L1 | 語法修復不自動 eligible |

| `Import明確證據` | 0 | 未觀察到可計數案例，不可宣稱不存在 | 未來 Domain API/tool import → L3；一般 missing import／NameError → 通常 L4 |

- Format／packaging：68
- Syntax：60

- Import 明確證據：0

- Truncation：80，且為與上述類別重疊的 mechanism 標記

- 不得把 Unknown 275 直接改稱 L5。
- 不得因 v3 認定 Entry-point 屬 L2，就覆寫舊報表的分類名稱或數量。

## 12. Development、Validation 與 Confirmatory evidence

分類結果可以統計，但必須按 evidence role 分帳。

| evidence_role | 可做的事 | 不可宣稱的事 |
|---|---|---|
| `historical_development` | 描述既有錯誤、形成假說、建立初版 codebook | 不可宣稱凍結後泛化或 confirmatory 成效 |
| `development` | failure census、頻率統計、規則發展、例案分析 | 不可當 validation／confirmatory |
| `validation` | 選版本、淘汰誤修規則、估計 validation 表現 | 不可改稱 confirmatory；若用於選擇即不再未見 |
| `confirmatory` | 在事前凍結條件下作正式推論 | 不可事後依個案修改規則再回填 |
| `post_hoc_exploratory` | 解釋異常、提出 vNext | 不可併入原 confirmatory 主分析 |

Development 結果可以且應該報告，例如：錯誤類別數量、mechanism 分布、候選 eligibility、規則來源與開發集 rescue；但標題、表格與結論必須明寫 `development evidence`，不可宣稱 validation、confirmatory、外部泛化或凍結後效果。

建議每張表至少包含：`dataset`、`evidence_role`、`split_id`、`model`、`condition`、`evaluator_revision`、分子與分母。

## 14. 共同判定流程

```text
0. 先鎖定 raw artifact、prompt、contract、runtime 與 evaluator revision。

1. 基礎設施是否可靠完成？
   否 → L0；outcome_validity = INVALID_INFRASTRUCTURE。

2. 是否取得唯一、可判定且可解析的 Python candidate？
   否 → L1。
   若原因為截斷，加 truncation；若為研究方 extractor，加 pipeline_extraction_error
   並將 validity 判為 INVALID_INFRASTRUCTURE。

3. G3e：entry point／signature 是否符合事前契約？
   否 → L2。
   唯一安全候選 → 可進 eligibility gate；多候選／不明 → ambiguous + abstain。

4. 執行是否成功？
   否 →
      Domain API／tool import 或使用錯誤 → L3；
      一般 missing import、變數、資料流、控制流程、遞迴或 timeout → L4；
      無法區分 → PENDING_REVIEW，不猜測。

5. 執行後 output schema／packaging／canonical form 是否符合？
   否 → L2。

6. required API 是否事前明定且符合？
   否 → L3；未事前明定不得事後補判。

7. 正式 correctness 是否通過？
   否 → 先排除 evaluator 錯誤；確認 evaluator 有效後才標 L5。

8. 全部適用 gate PASS → PASSED。

9. 另行判 outcome_validity；再以 evaluator-blind 規則判 Healer eligibility。
```

## 15. 統計與合併規則

### 15.1 原始生成

至少報告：

- planned cells、raw responses、valid candidates、G1／G2／G3／G4 PASS、final PASS；
- L0–L5 分布，且只把已 adjudicated 的 `VALID_MODEL_OUTCOME` 納入模型 failure-layer 主表；
- `outcome_validity` 完整分布；
- mechanism tags 的非互斥分布，明示每格可多標；
- `PENDING_REVIEW` 與無法 crosswalk 的數量；
- ITT pass rate 與 valid-response pass rate。

### 15.2 Healer

至少報告：

- processed、eligible、noneligible、triggered、transformed、abstained；
- rescue-to-pass、partial progress、unchanged fail、preserved pass、regression、rollback；
- verified rescue among eligible failing outputs；
- overall uplift among all outputs in the same split（同一 split 的全部輸出）；
- regression among originally passing outputs；
- outcome_validity × trigger／rescue 的分層表。

### 15.3 必須分開

- CE115／MBPP+／HumanEval+；
- historical development／development／validation／confirmatory／post-hoc exploratory；
- model、prompt condition、seed policy；
- evaluator revision 與 contract version；
- Observed／Pipeline-corrected／Post-Healer；
- production／experimental rule pack。

### 15.4 舊表與 v3 表的並列方式

建議同時報：

1. `Legacy census`：原分類與原數量，不變更。
2. `v3 adjudicated crosswalk`：只列完成逐筆審查且證據足夠的 subset，報 `n_reviewed / n_legacy`。
3. `Unresolved`：尚待審或 artifact 不足者，不塞入 L5。

不得用部分重審後的 L0–L5 分布冒充全部舊資料的新分布。

## 16. 共同研究紀律

1. L0–L5 記最早可觀察失敗層；mechanism tags 記形成原因；outcome validity 記責任；Healer 欄位記介入與結果。
2. 原始 artifact、first-attempt、舊分類與舊統計不可覆寫。
3. Unknown 不直接等於 L5；Truncation 不直接等於 L1。
4. Entry-point 錯誤固定歸 L2；唯一候選才可能 eligible，多候選必須 ambiguous／abstain。
5. Domain API／tool import 或使用錯誤歸 L3；一般 missing import／NameError 通常歸 L4。
6. Format／packaging 依最早 gate 拆為 L1 或 L2。
7. required API 必須事前明定；不得看到結果後補設 gate。
8. G4 FAIL 前先排除 L2 與 evaluator 問題。
9. Truncation 原則上 abstain，不把補全描述成安全 Healer。
10. Healer 不可用 oracle、測試結果或答案反推修法；L5 原則上不修。
11. Pipeline correction、evaluator revision 與 Healer rescue 分帳。
12. 修後重新跑相同版本的所有適用 G1–G4；partial progress 不等於 rescue。
13. 單題補丁、task ID 特例與答案常數不得算通用 Healer 規則。
14. machine label、人工標註、裁決結果與 disagreement 均保留。
15. development 可以統計並形成 development evidence，但不可冒稱 validation／confirmatory。
16. validation 用於選版後即不再是未見 confirmatory data。
17. 正式凍結後的新規則只能列 vNext／post-hoc exploratory，不回填原 confirmatory。
18. prompt、contract、toolbox、evaluator、rule pack 與 split 均保存版本及 hash。
19. 高 Healer 觸發率必須依 outcome validity 解釋，不得一概視為系統不成熟。
20. 合併分析前應裁決 PENDING_REVIEW；若因證據缺失無法裁決，須明列並排除於 L0–L5 分布，而非猜測。

---

## 17. 跨專案最小審查作業

為提高三組分類一致性，建議：

1. 先用共同 training examples 校準判定者，不使用正式 confirmatory 個案作教學。
2. 每個專案抽取預先固定比例，由兩名判定者獨立標註。
3. 判定者先看 raw、contract、gate evidence 與 exception，不先看 Healer 最終是否救回。
4. 保存 machine label、reviewer A、reviewer B、disagreement 與 adjudication。
5. 報百分比一致率；樣本與類別數足夠時再報 Cohen's kappa。
6. crosswalk 舊資料時，明列可取得的證據範圍；證據不足保留 legacy，不強制填新 layer。

## 18. v3 共同研究敘述

> 本研究以 G1–G4 判定 AI 生成 Python 程式在 candidate／parse、execution、contract 與 correctness 各 gate 的表現，並以 L0–L5 記錄 raw first-attempt 的最早可觀察失敗層。Truncation、format、entry point、import 等名稱不再同時充當症狀層、根因與可修復性結論，而是依最早 gate 與具體機制分開標記。`outcome_validity` 用於區分模型原生結果與 evaluator、contract、infrastructure 問題；Healer 的 eligibility、實際決策與修後結果另行分帳。此設計使 CE115、MBPP+ 與 HumanEval+ 能以共同欄位比較，同時保留各專案原始 artifact、舊分類、既有數量與 evidence role，不以新版 codebook 回頭改寫既有研究結果。
